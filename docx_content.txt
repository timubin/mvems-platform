SECTION 1 — EXECUTIVE SUMMARY

1. Product Overview & Vision
The Multivendor Event Management System (MVEMS) is a cloud-native, enterprise-grade SaaS platform designed to unify the complete lifecycle of event operations — from discovery and ticketing to real-time seat booking, vendor management, and post-event analytics. It serves four distinct personas: Super Admins, Organizers, Vendors, and Attendees, each with fine-grained role-based access controls.

1.1 Core Value Proposition
Eliminate double-booking through Redis-based distributed seat locking
Reduce organizer overhead with an end-to-end self-service dashboard
Maximize revenue with dynamic pricing, coupons, and multi-tier ticketing
Enable vendors to operate autonomously within an event ecosystem
Deliver real-time operational visibility via WebSocket-driven dashboards

2.2 Super Admin

Role Description
The Super Admin has unrestricted system access. Typically a platform operations team member. There is only ONE root Super Admin; additional admins can be promoted.

Permissions
Manage all user accounts (create, suspend, delete, impersonate)
Approve or reject organizer-submitted events
Access platform-wide analytics and revenue dashboards
Manage subscription plans and billing records
Force-cancel events and trigger bulk refunds
Configure system settings: payment gateways, email providers, feature flags
Access audit logs for all user actions
Manage MFA enforcement policies

2.3 Organizer

Role Description
Organizers are businesses or individuals who create and manage events. They operate within their own account namespace and can invite Staff members to their events.

Permissions
Create, edit, duplicate, and delete events
Define ticket tiers, pricing, and availability windows
Publish or unpublish events; submit for admin approval
View per-event sales, revenue, and attendee analytics
Process manual refunds and issue complimentary tickets
Manage vendor applications and booth assignments
Configure event sessions, speakers, and agenda
Export attendee lists (CSV/PDF)
Set event-specific discount codes and early-bird pricing

2.4 Vendor

Role Description
Vendors are businesses that apply to participate in events with a booth or stall. Each vendor operates independently within the events they are approved for.

Permissions
Browse open vendor calls for events
Submit booth application with business profile and requirements
Manage booth details: name, description, images, product catalogue
Track booth-level sales (if integrated with POS)
Communicate with Organizer via in-platform messaging
Access event logistics and setup schedule

2.5 Staff / Moderator

Role Description
Staff are invited by Organizers to assist in event operations. Their permissions are scoped to a single event and configured by the Organizer.

Permissions
Scan QR codes for attendee check-in
Manually override check-in status
View session schedules and speaker details
Flag incidents or issues to the Organizer
Access read-only attendee list for assigned sessions

2.6 Attendee (End User)

Role Description
Attendees are the end-consumers of the platform. They self-register, discover events, purchase tickets, and interact with event content.

Permissions
Register and manage personal profile
Browse and search all public events
Purchase and manage tickets (view, transfer, cancel)
Download e-tickets and QR codes
Submit post-event reviews and ratings
Manage notification preferences

System validates credentials against bcrypt hash

MODULE 05 — SEAT BOOKING ENGINE

Module 05: Seat Booking Engine
The Seat Booking Engine is the most technically critical module of the platform. It must guarantee zero double-bookings across thousands of concurrent users attempting to select the same seat simultaneously, using a Redis-based distributed locking strategy.


Critical System Note
This module uses Redis SETNX for atomic seat locking. The lock TTL is 5 minutes. If payment is not completed within this window, the lock is auto-released and the seat becomes available again.

05.3 Concurrency Control Flow
User A selects Seat S-12 → API receives request
System executes: SETNX seat:{event_id}:S-12 {user_A_session_id} EX 300
Redis returns 1 (success) → seat is locked for User A
User B simultaneously selects Seat S-12 → same SETNX command
Redis returns 0 (key exists) → User B receives 'Seat Unavailable' response
User A completes payment within 5 min → seat state set to BOOKED in DB
Redis lock key updated to permanent booking record
If User A abandons: TTL expires → key deleted → seat returns to AVAILABLE
WebSocket broadcasts state change to all connected clients in real time

All payment operations use idempotency keys to prevent duplicate charges in case of network failures or retries. Every payment attempt is logged with its full request/response payload.

07.2 Payment Flow
Successful Payment Flow
Order created in PENDING state → client requests payment intent
Server creates Stripe PaymentIntent with amount, currency, metadata (order_id)
Client receives client_secret → Stripe.js completes card entry client-side
Stripe processes payment → sends signed webhook to /api/webhooks/stripe
Webhook handler verifies Stripe-Signature header
Handler looks up order_id from metadata → updates Order to COMPLETED
Seat records updated to BOOKED; tickets generated with QR codes
Confirmation email triggered via Notification module
